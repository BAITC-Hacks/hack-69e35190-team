# Техническая спецификация: подбор подрядчиков

## Расширение реализации: каталоги и чат

Исходный контракт ниже сохранён для каталога default. POST /recommendations дополнительно принимает необязательный dataset_id и возвращает его в ответе. При его отсутствии используется исходный каталог. Новые CSV могут расширять словари городов, форматов и языков; дата проверяется по календарному периоду выбранного каталога. Исходные допустимые значения также остаются допустимыми.

POST /chat: `{message: string, slots?: object, pending_fields?: string[], dataset_id?: string}` → `{slots, pending_fields, missing_field, prompt, choices, warnings, parser, result, dataset_id}`. result содержит прежний ответ подбора, либо null до уточнения условий. slots использует имена структурированного контракта; language=null и duration_hours=null означают отсутствие соответствующего ограничения. Время начала не является входом фильтра, так как календарь подневный.

Клиент передаёт полученные `slots` **и** `pending_fields` в следующем сообщении и сбрасывает оба при новом поиске или смене каталога. Если явно указанное условие не удалось разобрать, старое значение исключается из `slots`, имя поля попадает в `pending_fields`, `missing_field=clarification`, `result=null`. Изменение другого поля не снимает это уточнение: нужно явно указать значение спорного поля или отменить необязательное ограничение. Например, после «на немецком» нельзя выполнить подбор без языка только потому, что следующим сообщением изменён бюджет.

«Не X, а Y» трактуется как замена значения; «6 часов 30 минут» — 6.5 часа; «в 15 часов на 3 часа» — 3 часа и предупреждение о подневном календаре. В двузначном году используется диапазон 2000–2099: `25.10.27` означает 2027 год и не подменяется годом каталога. Дата вне календаря возвращает ошибку валидации.

Если предыдущие `slots` полные и изменена только дата, в `result` дополнительно возвращается `date_comparison`: `{previous_date,event_date,message,changes:[{id,anon_name,change,reason,message}]}`. `change` равен `removed` или `added` для вышедших/вошедших в первую тройку; `reason` — `busy`, `available` или `rank`. Причины вычисляются из двух отфильтрованных списков и `busy_dates`, без повторного обращения к AI. Свободный профиль, вытесненный из первой тройки, получает `rank`, а не ложную причину занятости. При одновременном изменении других условий сравнение дат отсутствует.

GET /datasets → `{datasets:[{id,name,source,profile_count,synthetic_count,csv_sha256,calendar_start,calendar_end,cities,categories,event_types,languages,index_status,index_message}]}`.

Каждая запись также содержит `category_counts` — словарь «категория → число профилей» по всему выбранному CSV. Один профиль может учитываться в нескольких категориях; эти числа отличаются от числа кандидатов в конкретном городе.

POST /datasets: `{name,csv,calendar_start,calendar_end}` → метаданные опубликованного каталога. CSV передаётся строкой, до 2 МБ, UTF-8, те же поля; списки через |. Требуется явный период известной занятости. Данные публикуются только после проверки всех строк; ошибочный импорт не меняет старые каталоги. Исходный файл неизменяемый. Индексация асинхронная, состояния lexical/indexing/ready/degraded.

Метки города, категории, формата и языка нормализуются без учёта регистра при загрузке; каноническое написание не зависит от порядка строк. Исходные CSV и `description` не переписываются. Новые значения из импортированного каталога остаются допустимыми.

POST /datasets/index: `{dataset_id}` → метаданные; запускает построение индекса, если он отсутствует/неудачен. Повторный вызов при ready/indexing не создаёт параллельную задачу. Все маршруты локального демо без аутентификации; не предназначены для публикации в интернете.

---

Версия 1.0. Источник данных — [`datasets/hackathon dataset anonymized .csv`](../datasets/hackathon%20dataset%20anonymized%20.csv). Markdown-файл в `datasets/` служит представлением тех же данных; сервис читает CSV. В нём 66 профилей с уникальными `id`, 17 категорий, 13 профилей с `synthetic=True`. Города: Алматы (50 записей), Астана (15), Зарубежье (1). Один профиль может относиться к нескольким категориям. Цены «от» лежат в диапазоне 100 000–6 000 000 ₸. Календарь известен только на 23.09.2026–31.12.2026 включительно.

## Входной контракт

`POST /recommendations`, `Content-Type: application/json`, тело:

```json
{
  "city": "Алматы",
  "event_date": "2026-10-10",
  "event_type": "свадьба",
  "category": "Флорист",
  "budget_kzt": 500000,
  "duration_hours": 6,
  "language": "русский"
}
```

| Поле | Обязательное | Тип и смысл |
| --- | --- | --- |
| `city` | да | Строка: `Алматы`, `Астана` или `Зарубежье`. |
| `event_date` | да | Дата `YYYY-MM-DD` в известном окне календаря. |
| `event_type` | да | Одно из: `свадьба`, `той`, `корпоратив`, `конференция`, `юбилей`, `день рождения`. |
| `category` | да | Непустое название категории. Список категорий берётся из CSV, а не зашивается в API. Неизвестная или отсутствующая в городе категория приводит к `category_not_in_city`. |
| `budget_kzt` | да | Положительное целое число тенге; верхняя граница суммы, с которой сравнивается цена «от». |
| `duration_hours` | нет | Положительное конечное число часов или `null`. |
| `language` | нет | `русский`, `казахский`, `английский` или `null`. |

Перед сравнением строк удаляются крайние пробелы и выравнивается регистр; в ответе используются написания из CSV. Пустые обязательные строки, некорректные типы, отрицательные и нулевые числа, несуществующая дата, неизвестный город/формат/язык и дата вне календаря дают HTTP `400` с `{"error": "понятное описание ошибки"}`. За пределами календаря нельзя считать подрядчика свободным только потому, что дата не встречается в `busy_dates`. Необязательные поля можно опустить.

## Выходной контракт

Валидный запрос всегда возвращает HTTP `200`, в том числе при пустой выдаче:

```json
{
  "status": "matched",
  "message": "Найден 1 подходящий флорист в Алматы. До трёх не хватает: ещё 1 профиль занят 2026-10-10.",
  "candidate_count": 2,
  "eligible_count": 1,
  "exclusion_counts": {
    "busy": 1,
    "budget": 0,
    "format": 0,
    "language": 0,
    "duration": 0
  },
  "cards": [
    {
      "id": "HK-39372",
      "anon_name": "Тони Тони Чоппер",
      "category": "Флорист",
      "city": "Алматы",
      "price_from_kzt": 200000,
      "explanation": "Свободен 10 октября, берёт свадьбы; цена от 200 000 ₸ укладывается в бюджет 500 000 ₸. В описании указано авторское цветочное оформление мероприятий в Алматы.",
      "synthetic": false,
      "city_imputed": false,
      "price_imputed": true
    }
  ]
}
```

Пример отражает исходный CSV и запрос **без** `duration_hours` и `language`: это опциональные условия, поэтому они не упоминаются в объяснении. `price_from_kzt` — нижняя цена, а не подтверждённая стоимость заказа. При `price_imputed=true` интерфейс должен сообщать, что цену проставили при подготовке данных и её требуется уточнить. `synthetic=false` означает несинтетический профиль **исходного набора**, а не подтверждение личности подрядчика.

`candidate_count` — число профилей нужной категории в городе до остальных фильтров. `eligible_count` — число профилей после всех фильтров, до ограничения выдачи тремя карточками. `exclusion_counts` считает причины по каждому профилю; один профиль может одновременно быть занят и дороже бюджета, поэтому сумма значений может превышать `candidate_count - eligible_count`. Все пять ключей возвращаются всегда. `cards` содержит от нуля до трёх элементов.

Три пользовательских исхода:

| `status` | Условие | Обязательный смысл `message` |
| --- | --- | --- |
| `matched` | Есть хотя бы один прошедший профиль. | Сколько найдено и показано; если `eligible_count < 3`, почему карточек меньше трёх. |
| `category_not_in_city` | `candidate_count = 0`. | В указанном городе этой категории в каталоге нет. |
| `no_matches` | `candidate_count > 0`, `eligible_count = 0`. | Кандидаты есть, но ни один не прошёл; назвать фактические причины и их количества. |

Для `category_not_in_city` и `no_matches` возвращаются `cards: []`, а не ошибка или пустой экран. Неизвестную категорию можно обработать первым статусом с уточнением, что её нет в каталоге вообще. Ответы не содержат бронирования, заявки или обещания доступности после момента проверки.

## Загрузка и фильтрация

При загрузке CSV проверить обязательные столбцы, уникальность `id`, корректность цены и дат. Поля `categories`, `event_formats`, `languages`, `busy_dates` — списки через `|`. Пустой `max_hours` интерпретируется как `null`: для таких услуг ограничение длительности не применяется. Значения `synthetic`, `city_imputed`, `price_imputed` преобразуются из `True`/`False` и сохраняются в карточке. Данные не дополняются догадками во время запроса.

Пайплайн для каждого запроса:

1. Выбрать профили с точным совпадением `city` и включением `category` в `categories`. Если их нет — `category_not_in_city`.
2. Исключить профили, у которых `event_date` входит в `busy_dates`. Площадки проходят тот же календарный фильтр, что и люди.
3. Исключить профили, у которых `price_from_kzt > budget_kzt`, запрошенного `event_type` нет в `event_formats`, указанного `language` нет в `languages`, либо `duration_hours > max_hours` при непустом `max_hours`.
4. Для диагностики проверить **все** условия для каждого кандидата и собрать все причины исключения. Если прошедших нет — `no_matches`.
5. Упорядочить прошедших, взять первые три, собрать карточки и сообщения.

Цена «от», заполненная при подготовке CSV, всё равно участвует в фильтре бюджета, но её происхождение обязательно видно пользователю. У синтетического профиля должен быть заметный признак в карточке. Если команда добавит новые синтетические записи, одного `synthetic=true` недостаточно, чтобы отличить их от 13 исходных: потребуется отдельное поле происхождения или манифест добавленных `id`.

## Детерминированное ранжирование

Стартовый порядок среди **уже прошедших все жёсткие условия**: по `price_from_kzt` по возрастанию, при равенстве — по строковому `id` по возрастанию. Это прозрачное правило экономии бюджета, а не оценка качества подрядчика. Порядок строк в CSV и ответ LLM не должны влиять на него. При неизменных запросе и версии каталога порядок `id` в `cards` строго одинаков. Любое последующее изменение формулы ранжирования требует обновления этой спецификации и регрессионных сценариев.

Объяснение каждой карточки — 1–2 предложения на русском языке. Оно должно опираться на проверенные поля профиля и указывать конкретную деталь из `description`, если она релевантна запросу. Нельзя приписывать подрядчику неуказанные навыки, гарантировать итоговую цену или писать общую фразу вроде «отличный выбор». Когда дата меняется, в карточке указывается доступность **на новую дату**, а в `message` — сколько кандидатов исключены из-за занятости; сравнение двух ответов должно показывать изменение состава. Генерация объяснения не может менять допуск, статус или порядок карточек.

## Проверка реализации

- Плотная категория: `Алматы`, `2026-10-10`, `корпоратив`, `Ведущий`, `1500000` → `matched`: 10 кандидатов в городе, 5 проходят, 3 карточки. Порядок трёх `id` по стартовому правилу: `HK-88430`, `HK-29829`, `HK-27222`.
- Тот же запрос на `2026-10-11` → `matched`: 10 кандидатов, 4 проходят; первые три `HK-44923`, `HK-27222`, `HK-44733`. Состав выдачи меняется из-за календаря.
- Редкая категория: `Алматы`, `2026-10-10`, `свадьба`, `Флорист`, `500000` → `matched`: 2 кандидата в городе, 1 проходит (`HK-39372`), второй занят.
- Нет категории в городе: `Зарубежье`, `2026-10-10`, `свадьба`, `Флорист`, `500000` → `category_not_in_city` и `cards: []`.
- Кандидаты не проходят: первый запрос с бюджетом `1` ₸ → `no_matches`: 10 кандидатов, у всех цена «от» выше бюджета; возможны и другие причины исключения.
- Площадка: `Алматы`, `2026-11-14`, `свадьба`, `Банкетный зал`, `6000000` → `matched`: 7 кандидатов в городе, 2 проходят (`HK-64395`, `HK-90011`), в том числе один исходный синтетический профиль. Проверка `busy_dates` обязательна и для зала.

Ориентир времени ответа — до 10 секунд. Для 66 записей фильтрация и сортировка должны выполняться локально; внешний вызов для объяснений обязан иметь короткий тайм-аут и надёжный запасной вариант, чтобы не задержать ответ.

Полное ожидание каждого пользовательского AI-запроса ограничено 3 секундами, включая DNS, подключение и чтение медленного ответа. При исчерпании времени или доступных сетевых потоков выполняется локальный fallback. До двух последовательных внешних вызовов дают около 6 секунд ожидания; фоновая индексация имеет отдельный лимит. Браузер показывает измеренное время каждого ответа и отмечает превышение ориентира; ожидание ошибки в 12 секунд само по себе не считается выполнением критерия.
